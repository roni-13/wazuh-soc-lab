# PowerShell Process Detection

## Overview

This use case demonstrates detection of PowerShell process creation on a Windows endpoint using **Wazuh and Sysmon**.

PowerShell is a legitimate Windows administration tool but can also be abused by attackers for execution, scripting, and post-compromise activity.

## Detection Scenario

A PowerShell process is executed on the monitored Windows endpoint.

```text id="x3a2e1"
PowerShell Execution
       ↓
Sysmon Event ID 1
       ↓
Wazuh Agent
       ↓
Wazuh Manager
       ↓
Custom Rule 100020
       ↓
Wazuh Alert
```

## Sysmon Event

Sysmon **Event ID 1 — Process Create** provides process creation telemetry.

The event can contain important investigation fields such as:

* Image
* CommandLine
* ParentImage
* User
* ProcessId
* Hashes
* Timestamp

Example process:

```text id="f1g3q4"
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
```

## Custom Detection Rule

The lab uses custom Wazuh rule **100020** to detect PowerShell process creation.

```xml id="q7k2w8"
<rule id="100020" level="10">
    <field name="win.system.eventID">^1$</field>
    <field name="win.eventdata.image">(?i)powershell\.exe</field>
    <description>Custom PowerShell Process Detection</description>
    <group>windows,sysmon,powershell,process_creation,custom_detection,</group>
</rule>
```

## Detection Logic

The rule matches:

* Sysmon Event ID `1`
* Process image containing `powershell.exe`

When both conditions match, Wazuh generates a level 10 alert.

## MITRE ATT&CK Mapping

This detection is associated with:

| Field         | Mapping                                   |
| ------------- | ----------------------------------------- |
| Tactic        | Execution                                 |
| Technique     | T1059 — Command and Scripting Interpreter |
| Sub-technique | T1059.001 — PowerShell                    |

The MITRE mapping helps the analyst understand the potential attacker behavior represented by the detected activity.

## Investigation

When a PowerShell alert is generated, the analyst should review:

* PowerShell executable path
* Command line
* Parent process
* Executing user
* Timestamp
* Source/host information
* Process relationships
* Additional suspicious activity around the event

The command line is particularly important because benign administrative PowerShell activity and potentially malicious PowerShell activity can look very different.
